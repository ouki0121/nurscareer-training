ヨミ表マネジメント

CAのための在庫経営 ｜ あなたのヨミ表は「倉庫」。在庫を腐らせるか、売上に変えるか。

第1部：前提知識 — まず言葉を揃える

知っておくべき6つの言葉

取引
Deal
ヨミ表の1行のこと。「1人の求職者」ではなく「1回の転職支援」の単位。同じ人でも別の転職なら別の取引。
パイプライン
Pipeline
取引が受注に至るまでの流れ。工場のベルトコンベアのイメージ。フォーム回答→求まる→面接→内定→承諾→入金。
在庫
Inventory
パイプライン上にある全ての取引。加工待ちの素材。あなたのヨミ表の行数＝あなたの在庫数。
不良在庫
Dead Stock
動いていない取引。ステータスが変わらないまま放置されている。パイプラインを詰まらせ、新しい案件に手が回らなくなる原因。
ステータス
Status
取引が今パイプラインのどこにいるか。正しく管理する＝在庫の鮮度管理。AIが毎朝チェックする根拠。
受注角度
Win Rate
そのステータスから受注に至る確率。求まる済み=33%、面接セット=35%、内定提示=90%。金額×角度＝受注予測。

ナースキャリアのパイプライン（全体像）

全ての取引はこのパイプラインを通って売上になる。途中で止まったらMQLに戻り、誰かが掘り起こして再スタートする。
「クローズ」という概念はない。取引は死なない。必ずどこかに循環する。

理想のサイクル

フォーム回答から内定承諾まで、理想は30〜45日。
求まるから面接セットは7日以内。
面接後のフォローは当日中。
内定が出たら即日クロージング。
スピードが受注率を決める。

止まったら → MQLに戻る

音信不通、失注、対応不要… 理由は何であれ、止まった取引は全てMQLプールに戻す。
MQLは「共有在庫」。担当なし。誰でも掘り起こしOK。
掘り起こし成功 → 新しいレコードを作って再スタート。
入金後 → フォロー → 再転職・リファラルが生まれる → サイクルが回る。

求まる → 面接セット: 7日以内
面接 → 内定提示: 3〜7日
内定提示 → 承諾: 1〜3日
承諾 → 入金: 60〜90日
入金後 → フォロー: 2ヶ月スパン
第2部：在庫経営 — どこから売上を作るか

ヨミ表 = あなたの倉庫

あなたは倉庫の経営者です。在庫（取引）を仕入れて、加工して（アポ→求まる→面接）、出荷して（内定→承諾→入金）、出荷した顧客から次の仕入れを生む（リファラル・再転職）。

不良在庫が溜まると何が起こるか

フォーム回答が30件以上放置 → 新規リードに手が回らない
SQLの受注月が不確か → いつアタックすればいいかわからない
求まるから7日以上経過 → 求職者の温度が下がる

結果: パイプラインが詰まり、売上が止まる

正しく管理するとどうなるか

ステータスが常に最新 → AIが正確にタスクを出せる
不要な在庫はMQLに戻す → パイプラインがスッキリ
5つの源泉から計画的に仕掛ける → 目標達成の確度が上がる

結果: 毎朝Slackを見るだけで、今日やることがわかる

売上を作る5つの方法

「今月の新規リード何件来た？」だけで売上を考えていませんか？

第3部：運用ルール — ヨミ表を正しく管理する

ステータス変更の判断基準

「どうなったら、このステータスにする」の一覧。迷ったらこれを見る。

フォーム回答→SQL転職時期が先だが自分の取引として確保。受注月を必ず明記
フォーム回答→MQL転職時期不明・対応不要。プールに戻して誰でも掘り起こし可能に
フォーム回答→求まる済み初回アポ完了 + 求人探索完了 + 求人紹介済み
求まる済み→面接セット済み事まる取得 + 面接日程が確定
面接セット済み→内定提示面接合格 + 事業者から内定が出た
面接セット済み→不合格・再調整中面接不合格。別求人を探索 or MQLリリース
内定提示→内定承諾求職者が内定を承諾した
内定承諾→請求管理シート反映済み★請求管理シートに請求情報を記載完了
請求管理シート反映済み→入金確認済み入金を確認。入社後フォロー開始
どこからでも→MQL対応不要・紹介不可・音信不通・失注 → すべてMQLに戻す（クローズはない）

在庫の鮮度管理ルール（AIが毎朝チェック）

10件超

フォーム回答の滞留

アタックが疎かになっている。今必要ないならMQLかSQLに変更して在庫を整理

7日超

求まる済みの放置

事まる取得を急がないと求職者の温度が下がる。7日で鮮度切れ

20件超

SQLの滞留

受注月が不確か。コンタクトして時期を明確にするか、MQLに戻す

新しいレコード（行）を作るタイミング

既存の行を書き換えない。新しい行を追加する。元の行はそのまま残す。

MQLからの掘り起こし

1
MQLプールから候補を見つける
2
ヨミ表に新しい行を追加
3
I列（取引ソース）= 「掘り起こし」
4
E列 = 自分の名前 / U列 = コンタクト取れた日
5
以降は通常フロー。元のMQLレコードは触らない

早期退職からの再転職

1
早期退職の求職者に再転職の意向を確認
2
意向あり → ヨミ表に新しい行を追加
3
U列 = 再転職を進める言質を取れた日
4
求人探索 → 求まる取得から再スタート
!
意向なし → MQLにリリース
第4部：AIがサポートする — だからヨミ表を正しく管理する

毎朝8時、Slackにタスクが届く

AIがヨミ表を読み取り、あなた専用のタスクリストを自動生成します。
棚卸し・優先順位付け・異常検知・目標ギャップ計算 — 全部自動。
あなたは「考える」時間をゼロにして「動く」に集中できる。

在庫の棚卸し

5タイプの在庫を自動カウント。目標との差分を毎朝表示

優先順位付け

内定提示 → 面接フォロー → 求まる推進 → ... の順でタスクを並べる

異常検知

フォーム10件超・求まる7日超・SQL20件超を自動警告

ただし条件がある

ヨミ表のステータスが正しくないと、AIも正しく動けない。在庫の鮮度管理はCAの責任。
