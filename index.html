ヨミ表マネジメント

CAのための在庫経営 ｜ あなたのヨミ表は「倉庫」。在庫を腐らせるか、売上に変えるか。

第1部：前提知識 — まず言葉を揃える

これは「求職者管理」ではありません。「取引管理」です。

ヨミ表の1行は「1人の求職者」ではなく 「1つの取引」 です。
同じ求職者でも、転職活動が別なら別の取引（別の行）になります。
山田さんが2024年に転職して、2025年にまた転職するなら、それは2つの取引。
だから「掘り起こし」や「再転職」のときは、既存の行を書き換えずに新しい行を追加します。

知っておくべき用語

取引
Deal
ヨミ表の1行。「1人の求職者」ではなく「1回の転職支援」の単位。同じ人でも別の転職なら別の取引。
パイプライン
Pipeline
取引が受注に至るまでのベルトコンベア。フォーム回答→SQL→求まる→面接→内定→承諾→入金。1つだけ。全取引がここを通る。
供給源
Source
パイプラインに取引を投入する4つの蛇口。新規リード / SQL在庫 / MQLプール / 成約者フォロー。「今月どの蛇口を開けるか」を考えるのが在庫経営。
ステータス
Status
取引が今パイプラインのどこにいるか。正しく管理する＝在庫の鮮度管理。AIが毎朝チェックする根拠。
受注角度
Win Rate
そのステータスから受注に至る確率。求まる済み=33%、面接セット=35%、内定提示=90%。売上総利益×受注角度＝受注予測金額。
SQL在庫
SQL Inventory
自分がホールドした時期先の案件。受注予測月が3ヶ月以降のSQL。時期が来たらパイプラインに投入。自分だけの在庫で他のCAは触れない。
MQLプール
MQL Pool
担当なしの共有案件。誰でも掘り起こしOK。早い者勝ち。パイプラインで止まった取引はすべてここに戻る。
不良在庫
Dead Stock
動いていない取引。ステータスが変わらないまま放置。パイプラインを詰まらせ、新しい案件に手が回らなくなる原因。

ナースキャリアのパイプライン（全体像）

全ての取引はこのパイプラインを循環する。「クローズ」という概念はない。取引は死なない。
パイプラインで止まった取引 → MQLプールに戻る → 掘り起こしで再スタート。入金した取引 → フォロー → 再転職・リファラルが生まれる。

理想のセールスサイクル

フォーム回答から内定承諾まで、理想は30〜45日。
求まるから面接セットは7日以内。
面接後フォローは当日中。内定が出たら即日クロージング。
スピードが受注率を決める。

3つの循環ルート

1. MQLルート: 止まった取引 → MQLプールに戻る → 掘り起こし or SQL在庫確保 → 再スタート
2. 再転職ルート: 入金後 → フォロー → 再転職ニーズ発生 → 新レコード作成
3. リファラルルート: 入金後 → フォロー → 知人紹介 → 新規リードとして流入
この3つが回り続ける限り、パイプラインは枯れない。

フォーム回答 → 求まる: 7〜14日
求まる → 面接セット: 7日以内
面接 → 内定提示: 3〜7日
内定提示 → 承諾: 1〜3日
承諾 → 入金: 60〜90日
入金後 → フォロー: 2ヶ月スパン
第2部：在庫経営 — どの蛇口を開けるか

パイプラインに取引を供給する4つの蛇口

「新規リード何件来た？」だけで売上を考えるのはもったいない。

第3部：運用ルール — ヨミ表を正しく管理する

ステータス変更の判断基準

「どうなったら、このステータスにする」の一覧。迷ったらこれを見る。

フォーム回答→SQL転職時期が先だが自分の取引として確保。受注月を必ず明記（SQL在庫になる）
フォーム回答→MQL転職時期不明・対応不要。MQLプールに戻して誰でも掘り起こし可能に
フォーム回答→求まる済み初回アポ完了 + 求人探索完了 + 求人紹介済み
SQL（時期到来）→求まる済み受注月が到来。アタック → アポ → 求人紹介 → 求まる取得
求まる済み→面接セット済み事まる取得 + 面接日程が確定
面接セット済み→内定提示面接合格 + 事業者から内定が出た
面接セット済み→不合格・再調整中面接不合格。別求人を探索 or MQLリリース
内定提示→内定承諾求職者が内定を承諾した
内定承諾→請求管理シート反映済み★請求管理シートに請求情報を記載完了
請求管理シート反映済み→入金確認済み入金を確認。入社後フォロー開始（蛇口Dが動き始める）
どこからでも→MQL対応不要・紹介不可・音信不通・失注 → すべてMQLプールに戻す（クローズはない）

在庫の鮮度管理ルール（AIが毎朝チェック）

10件超

フォーム回答の滞留

アタックが疎かになっている。MQLかSQLに変更して整理を

7日超

求まる済みの放置

事まる取得を急がないと求職者の温度が下がる

20件超

SQL在庫の滞留

受注月が不確か。コンタクトして時期を明確にする

新しいレコード（行）を作るタイミング

既存の行を書き換えない。新しい行を追加する。元の行はそのまま残す。

MQLプールからの掘り起こし

1
MQLプールから候補を見つける
2
ヨミ表に新しい行を追加
3
I列（取引ソース）= 「掘り起こし」
4
E列 = 自分の名前 / U列 = コンタクト取れた日
5
以降は通常フロー。元のMQLレコードは触らない

早期退職からの再転職

1
早期退職の求職者に再転職の意向を確認
2
意向あり → ヨミ表に新しい行を追加
3
U列 = 再転職を進める言質を取れた日
4
求人探索 → 求まる取得から再スタート
!
意向なし → MQLプールにリリース
第4部：AIがサポートする — だからヨミ表を正しく管理する

毎朝8時、Slackにタスクが届く

AIがヨミ表を読み取り、あなた専用のタスクリストを自動生成します。
棚卸し・優先順位付け・異常検知・目標ギャップ計算 — 全部自動。
あなたは「考える」時間をゼロにして「動く」に集中できる。

4つの蛇口の棚卸し

各蛇口の取引数を自動カウント。目標との差分を毎朝表示

優先順位付け

内定提示 → 面接フォロー → 求まる推進 → ... の順でタスクを並べる

異常検知

フォーム10件超・求まる7日超・SQL在庫20件超を自動警告

ただし条件がある

ヨミ表のステータスが正しくないと、AIも正しく動けない。
在庫の鮮度管理はCAの責任。
